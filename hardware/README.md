# MCCAN Hardware

This is the KiCad 10.0.2 project for the ESP32 MCCAN lighting controller. The board is the
**plan4 board**: 140 × 100 mm, 8 layers, assembled by JLCPCB.

- Schematic spec: `../docs/superpowers/specs/2026-10-17-emarked-module-redesign-design.md`. The
  aux stage has its own spec: `../docs/superpowers/specs/2026-11-13-aux-stage-design.md`.
- Layout spec: `../docs/superpowers/specs/2026-11-13-board-layout-phase-b-design.md`.
- Ordering is in **`docs/fabrication.md`**, the harness in `docs/harness.md`, and routing in
  `docs/routing-tool.md`.

Everything here is generated by `scripts/`. Never hand-edit a `.kicad_sch`, `.kicad_pcb`,
`.kicad_pro` or `.kicad_dru`.

- **Stackup: 8 layers, 1.6 mm, 1 oz on every layer.**
  - Signals run on F.Cu, In2, In5 and B.Cu.
  - GND planes are on In1, In4 and In6, with GND_IN and GND_B islands.
  - In3 is power (VBAT, VBAT_B).
  - Feed B's 6.4 A runs on FEED_B_P pours on F.Cu, In5 and B.Cu.
  - There is no controlled impedance.
- **Assembly:** single-sided, top only, with every part placed by JLCPCB. The only THT parts are
  J2 and L2.
- **J2 (programming header) is fitted by JLCPCB, not left DNP.** L2 needs THT service anyway, and

  beside it. Normal updates go over WiFi (signed OTA).
- **Test pads:** 30 bare SMD pads (TP1–TP30), each labelled with its net name on the silkscreen.
  They are in two banks plus TP30 (GND_IN), and every bank is within clip reach of a GND pad. They
  are not in the BOM.
- **Cables:** one row on the bottom edge, through seven glands (`docs/harness.md` §2).

## Verification gates, in run order

Run from `hardware/`, with `K="/c/Program Files/KiCad/10.0/bin/kicad-cli.exe"`:

```
# 1. schematic
python scripts/gen_root.py && python scripts/gen_power_input.py && python scripts/gen_rails.py \
  && python scripts/gen_mcu_can.py && python scripts/gen_outputs.py
"$K" sch export netlist --format kicadsexpr -o output/netlist.net mccan.kicad_sch
"$K" sch erc --severity-error --exit-code-violations -o output/erc.rpt mccan.kicad_sch
python scripts/check_netlist.py

# 2. board (routes come frozen from scripts/routes_signal.json; see docs/routing-tool.md)
python scripts/gen_pcb.py && python scripts/gen_netclasses.py
"$K" pcb drc --severity-all --schematic-parity --refill-zones --exit-code-violations \
  -o output/drc.rpt mccan.kicad_pcb
ok=1; for c in frame placement antenna courtyards grounds zone_islands power_paths \
                plane_width plane_mincut vias geometry; do python scripts/check_$c.py || ok=0; done
python scripts/test_check_plane_mincut.py || ok=0; [ $ok = 1 ]

# 3. fabrication
python scripts/gen_fab.py && python scripts/gen_fab.py --check && python scripts/check_stock.py
```

**DRC must use `--refill-zones`.** Without it, every pad welded to a pour reads as unconnected.

**DRC must run at `--severity-all`.** `--severity-error` discards every rule set to `warning`:
silk, text and library metadata. `gen_netclasses.py` promotes the seven rules that can fail this
board's copper to `error` (`SEVERITIES`). But if a KiCad upgrade adds a rule that defaults to
`warning`, an error-only run would never see it.

The accepted residual is **zero**: 0 violations, 0 unconnected and 0 parity issues, at every
severity. With `--exit-code-violations`, any finding exits 5.

`check_plane_mincut.py` (about a minute) measures each power path's narrowest copper by max-flow
/ min-cut on a 0.1 mm raster, so it finds a neck at any angle. `check_plane_width.py` only cuts
along rows and columns, which can pass a diagonally necked pour; keep it as the fast first look.

`check_density.py` reports how full each region is. It is informational, not a gate.

## Board setup decisions

**Minimum track width and minimum connection width are both 0.15 mm, and they are tied on
purpose.** `min_connection` is the narrowest copper that may carry a connection. If it were set
above the thinnest legal track, every legitimately necked track would violate a rule that the same
file grants. Only the GND planes may neck further, to 0.12 mm between via antipads, through a
scoped rule in `mccan.kicad_dru` (`scripts/gen_netclasses.py`, `PLANE_NECK_RULE`).

**Reference designators are on F.Fab, except J\*, F\*, U\*, Q\*, D\* and L\*.**

- Test pads are identified on the silkscreen by their **net name** instead (`gen_pcb.tp_labels`).
- `gen_pcb.silk_refs` places each kept designator clear of every pad, of every other part's silk,
  of its own outline and of the board edge.
- Values are on F.Fab, so `output/jlcpcb/assembly.pdf` is a fully labelled copy.

The pin map and net names are the generators' (`scripts/gen_*.py`, `scripts/quadpins.py`) and the

### ESP32 pin rules that still hold

- GPIO 6-11 are the module's flash and are unusable. GPIO 37 and 38 are not bonded out.
- GPIO 34-39 are input-only and have **no internal pulls**. Here: 34 `SNS_A`, 35 `CAN_RXD`
  (RTC, EXT1 wake), 36 `SNS_B`, 39 `SNS_C`.
- ADC2 fails while Wi-Fi is up, so the sense inputs are all ADC1.
- Strapping pins, and what this board ties them to:
  - GPIO 0 is `BOOT_N`: the BOOT button SW1 and the auto-reset transistor Q3.
  - GPIO 2 is `DIAG_EN`: 4.7 k series, with R33 47 k pull-down on the chip side. It must be low
    for download, and the same pull-down holds the switches' `DIAG_EN` low. High level: 47 k ∥ 33.3 k
    (three chips at 100 k min) = 19.5 k, so 3.3 × 19.5 / (19.5 + 4.7) = 2.66 V against VIH 2.0 V.
  - GPIO 5 and 15 are `DIAG_SEL0` / `DIAG_SEL1`: 4.7 k series, **no pull** (their level is
    irrelevant while `DIAG_EN` is low). The three SEH internal pull-downs (100 k min each) load
    GPIO 15 against its internal pull-up, so the ROM boot log will probably be muted; that is
    harmless. Optional fix: a 10 k pull-up on the MCU side of R32 (not fitted).
  - GPIO 12 is `AUX_PWM_R`, the right pod's yellow PWM to U16 (2026-11-21), with R36 10 k to GND
    (flash voltage select, and the buffer input's pull-down). It is also the firmware's nominal TWAI
    TX pin: `CanBus::begin` hands it back to input + pull-down once TWAI starts, and only then does
    the firmware attach the right pod's LEDC channel. It must never be driven high through a reset.
- No lamp output sits on a strapping pin or on GPIO 14.

### Layout notes (honoured by the plan4 layout)

- **U10 (LTC4380) `ON` is tied to `VCC10`** (2026-11-15). It used to be left open on its internal
  1 Mohm pull-up, which needs < 1 uA leakage to ground: about 400 kOhm of moisture or flux would
  have held the whole board off. A 0.15 mm F.Cu track runs from pad 9 under the body to `VCC10`'s
  via. The old In1 keep-out and `check_power_paths` guard stay as belt-and-braces.
- `NT1` is the deliberate `GND_B` / `GND_IN` star point (connector side of L2, so no return current bypasses L2's return winding); place it deliberately (spec §4.1.1). It is a 2.0 mm tie so it outlasts the harness fuse when one feed is reversed while the other is connected.

### Bring-up checklist

- **ROM boot log may be absent.** The three SEH internal pull-downs load GPIO 15 (MTDO), so the boot ROM log is probably muted. Harmless. Optional fix: a 10 k pull-up on the MCU side of R32 (not fitted).
- **GPIO12 / flash voltage.** The TWAI driver needs a TX pin and drives it high; on this board that is GPIO12, the MTDI strap. Since 2026-11-15 `CanBus::begin` returns GPIO12 to input + pull-down right after `twai_start()` (listen-only never transmits), and R36 holds it low at every reset. Since 2026-11-21 GPIO12 is also `AUX_PWM_R`, the right pod's yellow PWM, attached only after `CanBus::begin`. Check on the bench: GPIO12 reads ~0 V while running with the right pod off, carries the pod PWM when it is on, and CAN frames still arrive. The optional permanent remedy is `espefuse.py set_flash_voltage 3.3V`, which is **IRREVERSIBLE** and is the owner's decision; it has not been run.
- **Diagnostics settling.** After any `DIAG_SEL` or `DIAG_EN` change wait >= 400 us before reading `SNS_x`.
- **Reverse polarity.** Test one feed reversed with the other disconnected, and the whole harness reversed. Test one feed reversed with the other connected only on a current-limited bench supply: that drives fault current through NT1 and the shared return until the harness fuse clears.
- `R100` (33 mOhm) sets feed A's limit at 1.36-1.67 A, between its ~0.87 A load and its ~2 A fuse (aux spec A10). Re-check it against the measured start-up current.
- **Shorted lamp vs feed A's limit.** The quads' ILIM is 0.25 A (R62-R64 56.2 k, since 2026-11-15; was 0.5 A). The MCU's rail is behind U10, so one short at 0.5 A (peaking 1.4x) on top of the 0.87 A worst case could reach U10's limit and reset the MCU in a loop. At 0.25 A a single short stays under it (~1.24 A) and that channel latches off. Check on a current-limited bench supply: with all lamps on, short one output to GND; the board must stay up and only that channel go dark. Two simultaneous shorts can still trip U10.
- **J2 is not an FTDI header.** Pin order 3V3 GND TX RX DTR RTS (labelled on the silk). A generic FTDI cable (GND CTS VCC TX RX RTS) puts GND on +3V3_ALW and 5 V on TXD0. Use the MCCAN programmer.
